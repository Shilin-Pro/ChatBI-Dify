# 问题总结：测试中发现的模型行为

这份文档记录评测中发现的具体问题，每个都有生成的 SQL 原文。按根因分类，不按错误表现。

---

## 一、时间处理

### 1.1 用 CURRENT_DATE 查历史数据，结果必然为空

**现象**：查「6月份的销售额」，返回空。

**生成的 SQL：**

```sql
SELECT SUM(pay_amount) AS total_sales
FROM orders
WHERE status = '已完成'
  AND order_date >= DATE_FORMAT(CURRENT_DATE, '%Y-01-01')
  AND order_date < DATE_FORMAT(CURRENT_DATE, '%Y-07-01')
```

**为什么错**：`CURRENT_DATE` 是 2026-11-15，算出来是 2026 年的区间。但数据全在 **2024 年**，区间不重叠，结果必然为空。

**同一个问题，另一次运行是对的：**

```sql
WHERE order_date >= '2024-01-01' AND order_date < '2024-07-01'
```

**这说明**：模型不是不会，是**不确定「上半年」指今年还是数据所在年**。温度设为 0 也挡不住这种歧义——两次运行做了不同的语义解释。

**修复方向**：在上下文里说死数据范围。

```
数据范围：2024-01-01 到 2024-06-30
禁止使用 CURRENT_DATE / CURDATE / DATE_SUB(CURRENT_DATE, ...) 等依赖当前时间的函数
所有时间条件必须用硬编码日期字符串
```

---

### 1.2 订单口径不一致

**现象**：问「有多少个订单」，模型有时加 `status='已完成'`，有时不加。

```sql
-- 版本 A
SELECT COUNT(*) FROM orders WHERE order_date >= '2024-04-01' AND order_date < '2024-05-01'

-- 版本 B
SELECT COUNT(*) FROM orders
WHERE status = '已完成' AND order_date >= '2024-04-01' AND order_date < '2024-05-01'
```

数据库里 4 月共 5 笔订单，其中 1 笔「待付款」。A 返回 5，B 返回 4。

**哪个对取决于业务口径**：

| 问法 | 正确口径 |
|---|---|
| 「有多少个订单」 | 全部（含未完成） |
| 「成交了多少单」「有效订单」 | 只算已完成 |

**这个问题的价值**：暴露了「口径」和「问题措辞」的对应关系没在 Prompt 里说清。

**注意**：我一开始把 A 判成错，是我的标准答案写错了——问「有多少订单」应该算全部。**测试失败时先怀疑标准答案。**

## 二、字段匹配

### 2.1 精确匹配 vs 模糊匹配

**现象**：问「MacBook Air 卖了多少件」，返回 0 或 1，正确答案 4。

数据库里商品名是 `MacBook Air M3`。

```sql
-- 精确匹配，匹配不到
WHERE p.name = 'MacBook Air'

-- 应该是模糊匹配
WHERE p.name LIKE '%MacBook Air%'
```

**同类问题在商品查询里很普遍**：

| 用户问 | 数据库实际 |
|---|---|
| iPhone 15 | Apple iPhone 15 128G |
| 罗技鼠标 | 罗技无线鼠标 |
| 华为 Mate60 | 华为 Mate 60 Pro |

**用户不会记住完整商品名。默认应该用 `LIKE`。**

**V3 的解决方案**：空数据时触发实体探测，用 `LIKE` 捞真实名称，再重写 SQL。5 个模糊问法全部命中。

## 三、聚合与数据源

### 3.1 用了不可信的预聚合字段

**现象**：问「深圳客户的消费总额」，返回 231700，正确答案 61991。

**生成的 SQL：**

```sql
SELECT SUM(total_spent) FROM customers WHERE city = '深圳'
```

**这不是模型蠢。** `total_spent` 字段名就叫「累计消费金额」，按语义用它天经地义。

**问题在数据建模**：这个冗余字段是造测试数据时写死的，和订单表实际汇总不一致。

实测对比：

| 口径 | 男性客户消费总额 |
|---|---|
| `SUM(customers.total_spent)` | **246950** |
| `SUM(orders.pay_amount)`（正确） | **64145** |

**差 3.8 倍。**

**关键认知**：

> 真实业务库里这种冗余统计字段很常见。模型无法判断「两个信息源冲突时该信哪个」。必须在文档里明确写数据源优先级。

**修复方向**：RAG 文档里写明「`customers.total_spent` 是历史遗留字段，不可信，统计消费额必须从 orders 表汇总」。

### 3.2 问总量返回明细

**现象**：问「东莞客户的总消费额」，返回两行明细而不是一个总数。

```
| total_spent |
|-------------|
|         199 |
|          59 |
```

模型生成了明细查询，没加 `SUM()`。正确应该是 258。

**「总」这个字没有稳定触发聚合。**

## 四、分类层级

### 4.1 二级分类查询写错

**现象**：问「电脑办公的销售额」，返回空。

**错误 SQL**：

```sql
WHERE p.category_id IN (
    SELECT c.id FROM categories c
    WHERE c.parent_id = (SELECT id FROM categories WHERE name = '电脑办公')
)
```

「电脑办公」是二级分类，没有子分类，这个子查询返回空。

**正确写法**：

```sql
WHERE p.category_id = (SELECT id FROM categories WHERE name = '电脑办公')
```

### 4.2 二级分类用了一级分类的范围

**现象**：问「女装的销售额」，返回 3961，正确答案 2364。多出来的 1597 是男装。

**错误 SQL**：

```sql
WHERE p.category_id IN (
    SELECT c.id FROM categories c
    WHERE c.parent_id = (SELECT id FROM categories WHERE name = '服装鞋包')
    UNION ALL
    SELECT id FROM categories WHERE name = '女装' AND parent_id IS NOT NULL
)
```

第一个子查询把「服装鞋包」的**所有**子分类都查出来了（男装 + 女装），第二个 UNION 又把女装加了一遍。

3961 = 2364（女装）+ 1597（男装）。

### 4.3 这个问题的反复性

| 版本 | 状态 | 原因 |
|---|---|---|
| V1（8900 字符 Prompt） | ✅ 正确 | Prompt 里有专门规则 + 2 个示例 |
| V2（506 字符 Prompt） | ❌ 退化 | 精简时这条规则被砍掉 |
| V2（加回第 6 条） | ✅ 正确 | 「查二级分类直接等值匹配，查一级分类必须包含子类」|

**关键认知**：

> 精简 Prompt 时不能只看字符数，要看规则覆盖度。

## 五、概念混淆

### 5.1 毛利率 vs 毛利

**现象**：问「哪个商品的毛利率最高」，返回 MacBook Air M3（利润总额 7196 元），正确答案不锈钢保温杯（毛利率 65.1%）。

**生成的 SQL 按利润总额排序：**

```sql
SELECT p.name, SUM((p.price - p.cost) * oi.quantity) AS total_profit
...
ORDER BY total_profit DESC LIMIT 1
```

**区别**：

| 概念 | 公式 | 含义 |
|---|---|---|
| 毛利 | `SUM((price-cost) × quantity)` | 绝对金额 |
| **毛利率** | `(price - cost) / price` | 百分比 |

MacBook Air 单价高，利润额大；不锈钢保温杯成本占比低，毛利率高。

**业务术语的歧义**：「毛利率」在口语里经常和「毛利」混用。模型选了常见但错误的那个。

### 5.2 销售额口径：GMV vs 实付

**现象**：问「6月份销售额」，返回 19114，正确答案 15284。

两个数都对，只是口径不同：

| 写法 | 数值 | 含义 |
|---|---|---|
| `SUM(oi.subtotal)` | 19114 | 商品原价小计（GMV） |
| `SUM(o.pay_amount)` | 15284 | 实际到账（扣整单优惠） |

差额 3830 = 6 月订单的优惠总额。

**更危险的情况：JOIN 明细后对订单金额求和**

```sql
-- 严重错误：金额被重复累加 N 次
SELECT SUM(o.pay_amount)
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
WHERE o.status = '已完成'
```

一笔订单有 5 条明细，`pay_amount` 就被加了 5 遍。

**这个 bug 是我修前一个 bug 时引入的**：为了修分类销售额，加了「销售额用 subtotal」规则，结果时间维度也被套用了。

**修一个 bug 引入另一个，是 Prompt 工程的常态。**

## 六、工程与配置

### 6.1 Prompt 被浏览器翻译污染

**现象**：工作流完全不可用。

**Prompt 实际内容：**

```sql
选择总和（oi.quantity）为 total_sales
来自 order_items oi
JOIN 命令 o on 的 oi.order_id = o.id
工会
精选
```

| 原文 | 被翻译成 |
|---|---|
| SELECT | 选择 |
| FROM | 来自 |
| JOIN | 在 |
| UNION | 工会 |
| CONCAT | 模糊 |
| WHERE | 其中 |

**原因**：浏览器网页翻译把 Dify 编辑器里的代码也翻了。

**教训**：**Prompt 必须在本地文件维护**，Dify 里只做部署。

### 6.2 直接改数据库导致 RAG 检索失效

**现象**：所有查询都失败，模型编造不存在的表名。

```
Table 'cd.product_categories' doesn't exist
```

**原因**：我直接改数据库更新知识库文档（删除分段 → 插入新内容 → 重建向量），破坏了 Dify 的内部状态（分段 ID、index_node_id 的一致性）。

**连锁反应：**

```
RAG 检索返回空 → 模型没有任何表结构参考 → 编造表名
→ SQL 报错 → 全部查询失败
```

**持续了 11 分钟。**

**教训**：**不要绕过框架直接改数据库**。Dify 的知识库不只是「文档 + 向量」，还有一套内部状态。

### 6.3 Code 节点误判（最隐蔽）

**现象**：V3 刚做完时 18 个用例全部失败。

**执行轨迹**：

```
SQL Query 返回: | total_spent |\n|---|\n| 63400 |     ← 有数据
Code 节点:      {"status": "empty"}                    ← 判成空
```

**根因**：

```python
# 旧代码：优先信 json
if not has_data:                    # sql_json 永远是 [{"data": []}]
    return {"status": "empty"}
```

插件在 markdown 输出模式下，`json` 字段永远是空数组，真实数据只在 `text` 里。

**后果**：所有查询判空 → 全部走纠错回路 → LLM4 把表名改成了 `product_category`、`users` → SQL 报错。

**修复后**：平均耗时 36.2s → 13.2s。

**这个案例的方法论价值**：

> 系统里任何一层判断出错，都会伪装成上一层的问题。

### 6.4 性能瓶颈不是模型慢

**现象**：单次查询 65 秒。

| 节点 | 耗时 | 占比 |
|---|---|---|
| SQL 生成（云端 V3） | 4.4s | 15% |
| **结果解读（本地 qwen3.5）** | **20s+** | **80%** |

**根因**：两个 LLM 节点的 `num_ctx` 不一致——生成 SQL 的是 4096，解读的是 14096。

14K 上下文的 KV cache 挤占了模型权重的显存空间（显卡 4GB，模型 3.49GB），导致更多层落到 CPU。

**统一降到 4096 后：65.6s → 19.1s。**

**方法论**：性能问题先做分解测量，不要猜。

## 七、问题归类

| 问题 | 根因 | 定性 |
|---|---|---|
| CURRENT_DATE 查历史数据 | 没告诉模型数据时间范围 | 上下文缺失 |
| 订单口径不一致 | 没定义「订单数」指什么 | 口径未定义 |
| 用不可信的 total_spent | 数据冗余不一致 + 没告知优先级 | **数据缺陷** |
| 问总量返回明细 | 模型偶尔忘加 SUM | 模型问题 |
| MacBook Air 精确匹配 | 用户不会记全名 | 模型问题 |
| 二级分类递归错误 | 精简 Prompt 时规则被砍 | 规则缺失 |
| 毛利率/毛利混淆 | 业务术语歧义 | 概念歧义 |
| 销售额口径选错 | 三种场景未明确区分 | 规则缺失 |
| Prompt 被翻译 | 浏览器行为 | 工具链问题 |
| RAG 检索返回空 | 直接改数据库 | 操作失误 |
| Code 节点判空 | 信了永远为空的 json 字段 | **代码 bug** |
| 性能瓶颈 | num_ctx 不一致 | 配置错误 |

**结论：这些问题里只有 2 个是纯模型能力问题，其余都是上下文、规则、数据、代码或配置的问题。**

---

## 八、一句话总结

**Text-to-SQL 的准确率瓶颈通常不在模型，而在你给它的信息是否充分、准确、无歧义。**
