# 问题总结：测试中发现的模型行为

这份文档记录评测过程中发现的具体问题，每个都有生成的 SQL 原文。

分类方式按**根因**，不按错误表现。

---

## 一、时间处理

### 1.1 用 CURRENT_DATE 查历史数据，结果必然为空

**问题**：查「6月份的销售额」，返回空。

**生成的 SQL：**

```sql
SELECT SUM(pay_amount) AS total_sales
FROM orders
WHERE status = '已完成'
  AND order_date >= DATE_FORMAT(CURRENT_DATE, '%Y-01-01')
  AND order_date < DATE_FORMAT(CURRENT_DATE, '%Y-07-01')
```

**为什么错**：`CURRENT_DATE` 是 2026-11-15，算出来是 `2026-01-01` 到 `2026-07-01`。但数据全在 **2024 年**。区间不重叠，结果必然是空。

**同一个问题，另一次运行生成的是对的：**

```sql
SELECT SUM(pay_amount) AS total_sales
FROM orders
WHERE status = '已完成'
  AND order_date >= '2024-01-01'
  AND order_date < '2024-07-01'
```

**这说明**：模型不是不会，是**不确定「上半年」指今年还是数据所在年**。同样的问题问两次，结果不同。

**同类问题：**

```sql
-- 查"最近一个月卖得多的商品"
AND o.order_date >= DATE_SUB(CURRENT_DATE(), INTERVAL 1 MONTH)
AND o.order_date < CURRENT_DATE()
```

数据是 2024 年的，`CURRENT_DATE()` 是 2026 年，同样是空。

**修复方向**：Prompt 或 RAG 文档里明确写死时间范围：

```
数据范围：2024-01-01 到 2024-06-30
禁止使用 CURRENT_DATE / CURDATE / DATE_SUB(CURRENT_DATE, ...) 等依赖当前时间的函数
所有时间条件必须用硬编码日期字符串
```

**这个问题的价值**：不是模型能力问题，是**上下文没告诉它数据在哪个时间段**。加一句数据范围说明就能解决大部分。

---

### 1.2 时间聚合口径不统一

**问题**：问「有多少个订单」，模型有时加 `status='已完成'`，有时不加。

```sql
-- 版本 A（正确，如果问的是全部订单）
SELECT COUNT(*) FROM orders
WHERE order_date >= '2024-04-01' AND order_date < '2024-05-01'

-- 版本 B（少算了未完成订单）
SELECT COUNT(*) FROM orders
WHERE status = '已完成'
  AND order_date >= '2024-04-01' AND order_date < '2024-05-01'
```

数据库里 4 月共 5 笔订单，其中 1 笔「待付款」。A 返回 5，B 返回 4。

**哪个对取决于业务口径**：

| 问法 | 正确口径 |
|---|---|
| 「有多少个订单」 | 全部（含未完成） |
| 「成交了多少单」「有效订单」 | 只算已完成 |

**这个问题的价值**：暴露了**「口径」和「问题措辞」的对应关系**没在 Prompt 里说清。

---

## 二、聚合与预聚合字段

### 2.1 直接用预聚合字段，绕过了明细表

**问题**：问「深圳客户的消费总额」，返回 231700，正确答案 61991。

**生成的 SQL：**

```sql
SELECT SUM(total_spent) FROM customers WHERE city = '深圳'
```

**为什么错**：`customers.total_spent` 是**冗余的预聚合字段**，造数据时写死了，和订单表实际汇总不一致。

**但从 SQL 角度，这个写法「看起来」是对的** —— 字段名就叫 `total_spent`（累计消费金额），按语义用它天经地义。

**两种写法的对比：**

| 写法 | SQL | 结果 | 说明 |
|---|---|---|---|
| 用预聚合字段 | `SUM(total_spent)` | 231700 | 快，但数据不准 |
| 用明细表汇总 | `SUM(o.pay_amount)` JOIN orders | 61991 | 慢，但准确 |

**这个问题的价值**：

1. **数据建模缺陷**：冗余字段没和主数据保持一致
2. **模型无法判断该信哪个**：两个信息源冲突时，模型不知道优先级
3. **真实系统里这个问题很常见**：很多业务库都有类似的冗余统计字段

**修复方向**：RAG 文档里明确写「`customers.total_spent` 是历史遗留字段，不可信，统计消费额必须从 orders 表汇总」。

---

### 2.2 单表查询性能问题

**问题**：问「深圳客户的消费总额」，如果写成明细表汇总：

```sql
SELECT SUM(o.pay_amount)
FROM customers c
JOIN orders o ON o.customer_id = c.id
WHERE c.city = '深圳' AND o.status = '已完成'
```

**这个 SQL 在你的数据量下没问题**（20 客户、30 订单），但真实场景会有性能隐患。

**如果表大（百万级订单）：**

| 方案 | 复杂度 | 说明 |
|---|---|---|
| 单表 `SUM(total_spent)` | O(n) 扫客户表 | 20 行，瞬间 |
| JOIN 明细汇总 | O(n×m) | 需要索引 + 可能临时表 |
| 预聚合物化视图 | O(1) 查询 | 但需要定时刷新 |

**这个问题的价值**：

**模型倾向于生成「语义正确」的 SQL，但不考虑性能。** 它不知道你的表有多大、有没有索引、能不能接受全表扫描。

真实项目里需要在 Prompt 或 RAG 文档里写性能约束：

```
数据规模：customers 约 20 行，orders 约 30 行，order_items 约 39 行
性能不是瓶颈，优先保证结果准确
```

**或者反过来（真实大库）：**

```
orders 表百万级，禁止对 orders 做全表扫描，时间范围必须走索引
优先使用预聚合字段 customers.total_spent（每日定时刷新）
```

---

### 2.3 聚合意识不足：问总量返回明细

**问题**：问「东莞客户的总消费额」，返回两行明细而不是一个总数。

**错误输出：**

```
| total_spent |
|-------------|
|         199 |
|          59 |
```

**说明**：模型生成了明细查询，没加 `SUM()`。正确应该是 258（199+59）。

**这个问题的价值**：**「总」这个字没有稳定触发聚合**。模型偶尔会返回明细。

## 三、字段匹配

### 3.1 精确匹配 vs 模糊匹配

**问题**：问「MacBook Air 卖了多少件」，返回 1，正确答案 4。

**数据库里商品名是** `MacBook Air M3`。

**模型可能生成的 SQL：**

```sql
-- 精确匹配，匹配不到（返回 NULL 或 0）
WHERE p.name = 'MacBook Air'

-- 应该是模糊匹配
WHERE p.name LIKE '%MacBook Air%'
```

**同类问题在商品查询里很普遍**：

| 用户问 | 数据库实际 | 需要 |
|---|---|---|
| iPhone 15 | iPhone 15 Pro | LIKE |
| 罗技鼠标 | 罗技无线鼠标 | LIKE |
| 华为 Mate60 | 华为 Mate 60 Pro | LIKE |

**这个问题的价值**：**用户不会记住完整商品名**。默认应该用 `LIKE`，除非明确问「精确叫 X 的商品」。

## 四、分类层级

### 4.1 二级分类查询退化成一級分类范围

**问题**：问「女装分类的销售额」，返回 3961，正确答案 2364。多出来的 1597 是男装。

**生成的 SQL：**

```sql
SELECT SUM(oi.subtotal) AS sales
FROM order_items oi
JOIN orders o ON o.id = oi.order_id AND o.status = '已完成'
JOIN products p ON p.id = oi.product_id
WHERE p.category_id IN (
    SELECT c.id FROM categories c
    WHERE c.parent_id = (SELECT id FROM categories WHERE name = '服装鞋包')
    UNION ALL
    SELECT id FROM categories WHERE name = '女装' AND parent_id IS NOT NULL
)
```

**为什么错**：第一个子查询把「服装鞋包」的**所有**子分类都查出来了（男装 + 女装），第二个 UNION 又把女装加了一遍。

3961 = 2364（女装）+ 1597（男装）。

**正确写法：**

```sql
SELECT SUM(oi.subtotal) AS sales
FROM order_items oi
JOIN orders o ON o.id = oi.order_id
JOIN products p ON p.id = oi.product_id
WHERE o.status = '已完成'
  AND p.category_id = (SELECT id FROM categories WHERE name = '女装')
```

**同类问题：查二级分类返回空**

```sql
-- 电脑办公是二级分类，没有子分类，这个子查询返回空
WHERE p.category_id IN (
    SELECT id FROM categories WHERE parent_id =
        (SELECT id FROM categories WHERE name = '电脑办公')
)
```

**这个问题的价值**：

1. **模型不理解「二级分类没有下级」** 这个结构约束
2. **这个问题在 V1（Prompt 8900 字符）里修好了，V2（RAG 版）又退化了** —— 因为规则从 Prompt 移到知识库后没被检索到
3. **RAG 检索的是「知识」，模型需要的是「指令」**：描述 `parent_id` 是什么 ≠ 告诉它「二级分类不要递归」

## 五、概念混淆

### 5.1 毛利率 vs 毛利

**问题**：问「哪个商品的毛利率最高」，返回 MacBook Air M3（利润总额 7196 元），正确答案不锈钢保温杯（毛利率 65.1%）。

**生成的 SQL：**

```sql
SELECT p.name AS product_name,
       SUM((p.price - p.cost) * oi.quantity) AS total_profit,
       SUM(oi.quantity) AS total_sold
FROM order_items oi
JOIN products p ON p.id = oi.product_id
JOIN orders o ON o.id = oi.order_id
WHERE o.status = '已完成'
GROUP BY p.id, p.name
ORDER BY total_profit DESC
LIMIT 1
```

**问题**：按**利润总额**排序，没按**毛利率**。

**区别：**

| 概念 | 公式 | 含义 |
|---|---|---|
| 毛利 | `SUM((price-cost) × quantity)` | 绝对金额 |
| **毛利率** | `(price - cost) / price` | 百分比 |

MacBook Air 单价高，利润额大；不锈钢保温杯成本占比低，毛利率高。

**这个问题的价值**：**业务术语的歧义**。「毛利率」在口语里经常和「毛利」混用。模型选了常见但错误的那个。

---

### 5.2 销售额口径：GMV vs 实付

**问题**：问「6月份销售额」，返回 19114，正确答案 15284。

**两个数都对，只是口径不同：**

| 写法 | 数值 | 含义 |
|---|---|---|
| `SUM(oi.subtotal)` | 19114 | 商品原价小计（GMV） |
| `SUM(o.pay_amount)` | 15284 | 实际到账（扣整单优惠） |

差额 3830 = 6 月订单的优惠总额。

**更危险的情况：JOIN 明细后对订单金额求和**

```sql
-- 严重错误：金额被重复累加 N 次
SELECT SUM(o.pay_amount)
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
WHERE o.status = '已完成'
```

一笔订单有 5 条明细，`pay_amount` 就被加了 5 遍。

**这个问题的价值**：**这是我在修之前 bug 时引入的**。为了修分类销售额，加了「销售额用 subtotal」规则，结果时间维度也被套用了。**修一个 bug 引入另一个 bug，是 Prompt 工程的常态。**

## 六、输入与配置

### 6.1 Prompt 被浏览器翻译污染

**现象**：工作流完全不可用。

**Prompt 实际内容：**

```sql
选择总和（oi.quantity）为 total_sales
来自 order_items oi
JOIN 命令 o on 的 oi.order_id = o.id
工会
精选
```

**对照表：**

| 原文 | 被翻译成 |
|---|---|
| SELECT | 选择 |
| FROM | 来自 |
| JOIN | 在 |
| UNION | 工会 |
| CONCAT | 模糊 |
| WHERE | 其中 |
| state | 州 |

**原因**：浏览器网页翻译把 Dify 编辑器里的代码也翻译了。

**教训**：**Prompt 必须在本地文件维护**，Dify 里只做部署。改完从文件粘贴，不要直接网页编辑。

---

### 6.2 知识库检索返回空（配置层）

**现象**：所有查询都失败，模型编造不存在的表名。

```
Table 'cd.product_categories' doesn't exist
```

**原因**：我直接改数据库更新知识库文档，破坏了 Dify 的内部状态（分段 ID、index_node_id 的一致性）。

**连锁反应：**

```
RAG 检索返回空
  → 模型没有任何表结构参考
  → 编造表名 product_categories（正确是 categories）
  → SQL 报错
  → 全部查询失败
```

**教训**：**不要绕过 ORM/框架直接改数据库**。Dify 的知识库不只是「文档 + 向量」，还有一套内部状态。

## 七、性能观察

### 7.1 耗时分布

20 次运行的平均值：

| 节点 | 模型 | 耗时 | 占比 |
|---|---|---|---|
| LLM（生成 SQL） | DeepSeek-V3（云端 API） | **4.4s** | 15% |
| SQL Query | MySQL | 0.06s | 0.2% |
| **LLM 2（解读）** | qwen3.5:4b（本地） | **20s** | **80%** |
| Knowledge Retrieval | bge-m3 | 1.0s | 4% |

**结论**：**瓶颈在本地解读模型，不在 SQL 生成。**

SQL 生成走云端，4 秒就出来了。本地 qwen3.5:4b 生成 400 字符分析要 20 秒——显卡 4GB，模型 3.49GB 只能装 50% 进 GPU。

### 7.2 优化前后

| 配置 | 平均耗时 |
|---|---|
| num_ctx = 14096（LLM2） | 65.6s |
| **num_ctx = 4096** | **19.1s** |

**只改一个参数，快 3.4 倍。**

原因：14K 上下文的 KV cache 太大，挤占了模型权重的显存空间，导致更多层落到 CPU。降到 4K 后显存够用，GPU 占比从 46% 提到 50%。

## 八、汇总：哪些是模型问题，哪些不是

| 问题 | 根因 | 归类 |
|---|---|---|
| CURRENT_DATE 查空 | 没告诉模型数据时间范围 | **上下文缺失** |
| 订单口径不一致 | 没定义「订单数」指全部还是已完成 | **口径未定义** |
| 用预聚合字段 total_spent | 数据冗余不一致 + 没告知优先级 | **数据缺陷** |
| 问总量返回明细 | 模型偶尔忘加 SUM | **模型问题** |
| MacBook Air 精确匹配 | 用户不会记全名 | **模型问题** |
| 二级分类递归错误 | 知识描述了但没给指令 | **规则缺失** |
| 毛利率/毛利混淆 | 业务术语歧义 | **概念歧义** |
| 销售额口径选错 | 三种场景未明确区分 | **规则缺失** |
| Prompt 被翻译 | 浏览器行为 | **工具链问题** |
| RAG 检索空 | 直接改数据库 | **操作失误** |

**这张表的价值**：**11 个问题里只有 2 个是纯粹的模型能力问题**，剩下 9 个是上下文、规则、数据或工具链的问题。

这说明：**Text-to-SQL 的准确率瓶颈通常不在模型，而在你给它的信息是否充分、准确、无歧义。**
