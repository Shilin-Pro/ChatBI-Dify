# 两版对比：Prompt 硬编码 vs RAG 检索

这个项目做了两个版本，核心区别是**表结构怎么给到大模型**。

结论先放这：**5 张表的规模下，RAG 没有带来准确率提升，但改进了可维护性。RAG 的价值要到 20 张表以上才显现。**

## 一、两个版本的区别

| | V1：Prompt 硬编码 | V2：RAG 检索 |
|---|---|---|
| 表结构位置 | 直接写进 System Prompt | 存知识库，按问题检索注入 |
| Prompt 长度 | **12814 字符** | **506 字符** |
| 生成 SQL 的模型 | DeepSeek-V3（云端 API） | DeepSeek-V3（同） |
| 解读结果的模型 | qwen3.5:4b（本地） | qwen3.5:4b（本地） |
| 额外节点 | 无 | Knowledge Retrieval + Code |
| 工作流节点数 | 7 | 9 |

### V1 的 Prompt 结构（12814 字符）

```
角色定义
核心安全与格式红线（5 条）
数据库表结构（5 张表的完整 DDL + 字段说明）
核心关联关系
必守业务规则（11 条）
复杂查询示例（10 个）
```

### V2 的 Prompt 结构（506 字符）

```
角色定义
核心生成红线（4 条）
数据库表结构信息 ← {{#context#}} 由 RAG 注入
```

**V2 的表结构不在 Prompt 里**，而是由知识库节点检索后通过 `{{#context#}}` 注入。

## 二、准备差异

| 项目 | V1 | V2 |
|---|---|---|
| 改表结构 | 改 Prompt（12814 字符里找位置） | 改知识库文档 |
| 加业务规则 | 改 Prompt，容易和已有规则冲突 | 加文档段落 |
| 规则超过 15 条 | Prompt 臃肿，开始互相干扰 | 拆成多个文档 |
| 新人接手 | 要读懂 12814 字符的 Prompt | 看知识库文档 |

**V2 在这点上确实更好。** V1 改到 11 条规则时，我已经踩过「加一条规则破坏另一条」的坑（详见 `docs/v1-issues.md`）。

## 三、准确率对比

⚠️ **两版的测试集不同，不能直接比数字。** 下表只标注各项能力的有无。

| 能力 | V1 | V2 |
|---|---|---|
| 基础计数（有多少客户） | ✅ | ✅ |
| 时间维度销售（6月销售额） | ✅ 修过口径 bug | ✅ |
| **一级分类查询**（数码电器） | ✅ | ✅ |
| **二级分类查询**（电脑办公/女装） | ✅ **正确** | ❌ **退化了** |
| 多表关联 | ✅ | ✅ |
| 商品销量 | ✅ | ✅ |
| 错误兜底（问不存在的字段） | ✅ | ✅ |
| 空数据判断 | 靠 LLM 判断 | Code 节点判断 |

### 关键差异：二级分类查询

**V1 生成的 SQL（正确）：**

```sql
WHERE p.category_id = (SELECT id FROM categories WHERE name = '电脑办公')
```

**V2 生成的 SQL（错误）：**

```sql
WHERE p.category_id IN (
    SELECT id FROM categories WHERE parent_id = (SELECT id FROM categories WHERE name = '电脑办公')
)
-- 电脑办公是二级分类，没有子分类，结果为空
```

**为什么 V2 会退步：**

V1 的 Prompt 里有一条专门的规则：

```
分类查询（关键，容易写错）：
- 问一级分类 → 包含所有子分类，用 UNION 递归
- 问二级分类 → 直接等值匹配，禁止递归
```

规则在 12814 字符里有足够的篇幅写清楚，还有 2 个示例。

**V2 精简到 4 条规则时，这条被砍掉了。** 知识库文档里虽然描述了 `parent_id` 的含义，但**没有明确说「二级分类不要递归」**这个动作指令。

**教训：RAG 检索的是「知识」，但模型需要的是「指令」。** 描述性的知识容易被忽略，明确的规则不容易。

## 四、V2 新增的故障面

V2 多了两个节点，也多出三个可能出问题的地方：

| 故障点 | 表现 | 实际遇到过 |
|---|---|---|
| **RAG 检索失败** | 返回空，模型瞎猜表名 | ✅ 遇到过，编造了不存在的 `product_categories` 表 |
| **Code 节点判断错** | 把正常数据判成空 | 未遇到 |
| **索引不一致** | 主库有内容但检索不到 | ✅ 遇到过，改文档后检索全空 11 分钟 |

### 最严重的一次事故

我在更新知识库文档时，**直接操作了数据库**（删除分段 → 插入新内容 → 重建向量）。

结果是：**RAG 检索返回空，持续了 11 分钟**。

那段时间内所有查询都失败，因为：
1. RAG 找不到表结构
2. LLM 没有任何参考，编造了不存在的表名（`product_categories`）
3. SQL 执行报错：`Table 'cd.product_categories' doesn't exist`

**根本原因**：Dify 的知识库不只是「文档 + 向量」，还维护着一套内部状态（分段 ID、`index_node_id`、关键词等）。直接改数据库绕过了这套机制。

**正确做法**：在 Dify 界面里编辑文档，让它自己重新分段和建索引。

**这个事故说明：V2 的可维护性优势是有代价的——多了一层需要维护的组件。**

## 五、什么时候该用 RAG

算一下实际数据量：

| 表数量 | 完整表结构 token 数 | 建议 |
|---|---|---|
| **5 张（当前）** | **约 400** | **直接塞 Prompt** |
| 20 张 | 约 1600 | 还可以塞 |
| **50 张** | **约 4000** | **开始需要 RAG** |
| 100 张 | 约 8000 | 必须 RAG |
| 500 张 | 40000+ | RAG + 两阶段检索 |

**关键参考**：云端模型现在普遍支持 32K~128K 上下文。只要**表结构能塞进上下文的一半**，就不需要 RAG。

你的 5 张表 = 400 token，DeepSeek-V3 支持 64K。**用不到 1%。**

## 六、我的结论

**对当前项目：V1 更合适。**

| 维度 | 谁更好 |
|---|---|
| 准确率 | V1（分类查询没退化） |
| 可靠性 | V1（少两个节点，少三个故障点） |
| 可维护性 | V2 |
| 扩展性（表变多） | V2 |

**但 V2 不是白做的。** 它证明了三件事：

1. **知道什么时候不该用某个技术** —— 5 张表上 RAG 是过度设计
2. **RAG 的真正价值在规模** —— 表多了才显现
3. **抽象层的代价** —— 每加一层就多一处可能故障

## 七、如果要继续演进

**短期（表少于 20 张）**：保持 V1 的思路，把关键规则写进 Prompt，用文档管理版本。

**中期（表 20~50 张）**：
- RAG 检索表结构
- **但把「动作指令」留在 Prompt 里**（比如「二级分类不要递归」）
- 知识库只放「事实」（表有哪些字段、字段含义）

**长期（表 50 张以上）**：
- 两阶段检索：先检索相关表，再检索表内字段
- 加 few-shot 示例检索（从历史正确 SQL 里找相似案例）

**这个分层思路比单纯的「用不用 RAG」更重要。**

V1 和 V2 的工作流都存在 Dify 里，可以切换：

```bash
# 查看所有工作流应用
wsl -e bash -lc "docker exec docker-db_postgres-1 psql -U postgres -d dify -c \"
SELECT name, mode FROM apps WHERE mode='workflow';\""
```

| 应用名 | 版本 |
|---|---|
| `数据库查询` | **V2（RAG 版）** |
| `大型数据库查询-rag增强版` | 早期 RAG 尝试 |

V1 的 Prompt 完整版见 `prompts/llm1-sql-generator-v1-full.txt`（12814 字符）。
