# 三个版本的演进

这份文档记录 V1 → V2 → V3 的实际变化。所有配置都从 Dify 数据库的历史版本导出核实过。

## 一、总览

| | V1 | V2 | V3 ReAct |
|---|---|---|---|
| SQL 生成模型 | qwen3.5:4b（本地） | **DeepSeek-V3（云端）** | DeepSeek-V3（云端） |
| SQL 生成 Prompt | **8900 字符** | **506 字符** | 1486 字符 |
| 表结构来源 | 内联在 Prompt | **RAG 检索 top_k=4** | RAG 检索 top_k=6 + Rerank |
| 结果解读模型 | qwen3.5:4b | qwen3.5:4b | qwen3.5:4b |
| 节点数 | 7 | 9 | 16 |
| 纠错回路 | 无 | 无 | 2 条 |

工作流文件：`chatbi_v1.json` / `chatbi_v2.json` / `chatbi_v3_react.json`

Prompt 文件：`prompts/llm1-sql-generator-v1.txt` / `-v2.txt` / `-v3.txt`

---

## 二、V1 → V2：换模型 + 串 RAG

### V1 为什么 Prompt 要 8900 字符

V1 用本地 qwen3.5:4b 生成 SQL。这个模型对表结构和业务规则的理解有限，所以只能在 Prompt 里把话说满：

```
8900 字符 =
  完整表结构（每张表的每个字段都有含义说明）
  + 11 条业务规则（分类递归、销售额口径、时间过滤、JOIN 约束……）
  + 9 个完整查询示例
```

**当时的判断**：模型不够强，就把能想到的情况都写进去。

**问题**：规则越加越多，开始互相干扰。加一条「销售额用 subtotal」修好了分类统计，结果时间维度也被套用，又出了新 bug。

### V2 为什么能砍到 506 字符

换成 DeepSeek-V3 之后，两个变化同时发生：

1. **模型理解力上来了**，规则说清就行，不需要那么多示例
2. **表结构改由 RAG 检索注入**，不再占 Prompt

V2 的 Prompt 全文：

```
你是一个极其严谨的 MySQL 8.0 数据查询专家。请将用户的自然语言需求转换为纯文本 SELECT 语句。

# 用户需求
{{#用户输入节点.text#}}

# 数据库表结构信息
{{#context#}}

# 🚨 核心生成红线（必须严格遵守）
1. **纯文本输出**：只能输出单条 SQL，绝对禁止使用 ```sql 等 Markdown 标记！绝对禁止在末尾加分号 `;`！
2. **字段约束**：只能使用上面【表结构】中提供的真实表名和字段，绝不允许瞎编数据库中不存在的表或字段（严禁跨方言瞎写）。
3. **时间过滤**：绝对禁止使用 `YEAR()` 或 `MONTH()` 函数，必须使用范围查询（如 `order_date >= '2024-03-01' AND order_date < '2024-04-01'`）。
4. **业务口径**：统计营收/销量时，必须过滤 `status = '已完成'`。算商品销售额，必须用 `SUM(order_items.subtotal)`，绝不能用 `SUM(orders.pay_amount)`（防止金额重复累加）。
```

**只剩 4 条红线，0 个示例。**

### 这个变化说明了什么

> **Prompt 该多长，取决于模型有多强。**
>
> 本地 4B 需要在 Prompt 里铺垫大量细节和示例；云端 V3 理解力够，规则说清就够用。把 8900 字符的经验直接搬到 V3 上，是浪费 token；把 506 字符的写法迁到本地 4B 上，会大幅掉点。

### 顺带踩的坑

精简 Prompt 时丢掉了一条规则：「查二级分类直接等值匹配，查一级分类必须包含子类」。

结果 V2 一开始二级分类查询全错：

```sql
-- 报「电脑办公」，模型生成了找子分类的 SQL
WHERE p.category_id IN (
    SELECT id FROM categories WHERE parent_id =
        (SELECT id FROM categories WHERE name = '电脑办公')
)
-- 电脑办公没有子分类，返回空
```

**后来在 V2 的 Prompt 第 6 条加回去才解决。**

**教训：精简 Prompt 时不能只看字符数，要看规则覆盖度。**

## 三、V2 → V3：加纠错闭环

### V2 的死穴

用户说法和数据库实际值对不上：

| 用户问 | 数据库里实际是 | V2 结果 |
|---|---|---|
| MacBook 卖了多少 | MacBook Air M3 | ❌ 0（精确匹配失败） |
| iPhone 卖了多少 | Apple iPhone 15 128G | ❌ 0 |
| 罗技鼠标卖了多少 | 罗技无线鼠标 | ❌ 0 |

SQL 用 `= 'MacBook'` 查不到，返回空。V2 只能告诉用户「查无数据」。

### V3 加的两条回路

**回路一：实体消歧**

```
SQL 返回空
   ↓
LLM 3（实体探测器）
   Prompt: "因为上一次查询返回了空数据，说明用户输入的实体名称不准确。
            请提取用户问题中的核心实体，生成一句用于模糊匹配真实名称的 SQL。"
   规则: 只能查 products.name 或 customers.name，必须用 LIKE '%实体%'
   ↓
   输出示例: SELECT name FROM products WHERE name LIKE '%苹果%' LIMIT 5
   ↓
执行探测 SQL
   ↓
Code (1) 判断结果
   ├─ 找到 → 进入回路二
   └─ 没找到 → Output 2 友好提示
```

**回路二：SQL 重写**

```
LLM 4 的 Prompt：
  "你是一个极其严谨的 MySQL 8.0 填词专家。
   {原 SQL}
   已经证实了该 sql 里面实体不对，您只需要将该 sql 语句里面的实体进行替换即可
   我们在数据库中探测到，该实体的真实名称可能是：{探测结果}
   请根据上述真实名称，生成最终统计的 SQL 语句。"
```

**设计意图**：跳过 Schema 重新注入，只把原 SQL 和真实实体给模型，降低二次生成引入新错误的概率。

⚠️ **不要说成「100% 保留 JOIN 逻辑」** —— Prompt 只说「只替换实体」，模型仍可能改动其他部分。准确说法是「降低了改动的概率」。

### 实际效果

| 测试问题 | V3 结果 |
|---|---|
| MacBook 卖了多少件 | ✅ 4 件 |
| iPhone 卖了多少件 | ✅ 1 件 |
| 罗技鼠标卖了多少件 | ✅ 5 件 |
| 华为手机卖了多少件 | ✅ 2 件 |
| 林峰花了多少钱 | ✅ 17697 元 |

**5 个模糊问法全部命中。** 这是 V3 相比 V2 最实际的价值。

### 代价

节点从 9 个增加到 16 个，多了 2 次 LLM 调用（LLM3 + LLM4）和 2 次 SQL 执行。

**但这些只在「查询返回空」时才触发**，正常情况下不会多花时间。

## 四、V3 的一个大坑：Code 节点误判

V3 刚做完时，18 个测试用例全部失败。

### 现象

```
SQL Query 返回: | total_spent |\n|---|\n| 63400 |     ← 明明有数据
Code 节点输出:  {"status": "empty", "message": "查无数据"}   ← 判成空
```

### 根因

```python
# 旧代码
if not has_data:                    # has_data 来自 sql_json
    return {"status": "empty"}

# 而 sql_json 永远是 [{"data": []}]
```

**插件 `junjiem/db_query` 在 markdown 输出模式下，`json` 字段永远是空数组。**

真实数据只在 `text` 字段里。代码却「优先信 json」，所以永远判空。

### 连锁反应

```
所有查询判空
  → 全部触发纠错回路
  → LLM3 用「6月」去 products.name 里 LIKE（当然找不到）
  → LLM4 重写时把表名改成了 product_category / users
  → SQL 报错
  → 全部失败
```

### 修复后的 Code 节点

```python
def main(sql_text: str, sql_json: list) -> dict:
    sql_text = sql_text or ""
    sql_json = sql_json or []

    # 1. 报错
    if "SQL 执行失败" in sql_text or "抱歉" in sql_text or "error" in sql_text.lower():
        return {"status": "error", "message": "SQL执行出错"}

    # 2. json 有真实数据 → 成功
    if isinstance(sql_json, list):
        for item in sql_json:
            if isinstance(item, dict) and len(item.get("data") or []) > 0:
                return {"status": "success", "message": "正常"}
            if item and not isinstance(item, dict):
                return {"status": "success", "message": "正常"}

    # 3. json 没数据时看 text
    lines = [ln.strip() for ln in sql_text.split("\n") if ln.strip()]
    if not lines:
        return {"status": "empty", "message": "查无数据"}

    if len(lines) == 1 and not lines[0].startswith("|"):
        return {"status": "success", "message": "正常"}

    # 4. 解析 Markdown 表格，判断数据行是否全空
    data_lines = []
    for ln in lines:
        if not ln.startswith("|"):
            continue
        cells = [c.strip() for c in ln.strip("|").split("|")]
        if all(set(c) <= set("-: ") for c in cells):
            continue
        data_lines.append(cells)

    if len(data_lines) <= 1:
        return {"status": "empty", "message": "查无数据"}

    for cells in data_lines[1:]:
        if any(c for c in cells):
            return {"status": "success", "message": "正常"}

    return {"status": "empty", "message": "查无数据"}
```

**三层兜底**：

| 层 | 判断依据 | 覆盖场景 |
|---|---|---|
| 1 | json 数组有数据 | 插件返回结构化数据时 |
| 2 | 单行纯文本 | 聚合查询（COUNT/SUM 返回单值）|
| 3 | Markdown 表格数据行非空 | 标准表格查询 |

### 效果

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 平均耗时 | 36.2s | **13.2s** |
| 准确率 | 0/18 | **17/18** |

**这个案例的价值**：

> 系统里任何一层判断出错，都会伪装成上一层的问题。表面看是「模型生成了错误表名」，查执行轨迹才发现第一次生成的 SQL 完全正确——是代码节点误判把它送进了纠错回路。

## 五、选型结论

### 中小规模（< 20 张表）

**建议 V1 的做法**：表结构直接内联 Prompt。5 张表的结构约 400 token，云端模型支持 64K，用不到 1%。

**但模型要用云端的**，不要用本地小模型硬堆 Prompt。

### 中等规模（20~50 张表）

**建议 V2 的做法**：RAG 检索表结构。但要**把「动作指令」留在 Prompt 里**（如「二级分类不要递归」），知识库只放「事实」（表有哪些字段、字段含义）。

**关键认知**：RAG 检索的是「知识」，模型需要的是「指令」。描述 `parent_id` 是什么 ≠ 告诉它「二级分类不要递归」。

### 大规模（> 50 张表）

需要两阶段检索：先检索相关表，再检索表内字段。加 few-shot 示例检索（从历史正确 SQL 里找相似案例）。

### 用户输入不规范时

加 V3 的纠错回路。这是真实场景里最常见的一类失败——用户记不住完整的商品名、客户名。

## 六、一句话总结

| 版本 | 解决了什么 | 引入了什么 |
|---|---|---|
| V1 | 功能跑通 | Prompt 膨胀到 8900 字符，难维护 |
| V2 | 换云端模型 + RAG，Prompt 降到 506 字符 | 精简时丢规则，二级分类查询退化 |
| V3 | 加纠错回路，解决模糊实体匹配 | 节点数翻倍，Code 节点出过严重 bug |
