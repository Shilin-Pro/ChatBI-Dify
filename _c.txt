明确混合架构的设计理由：数据流向决定模型部署位置

## 架构说明

之前文档只写了"SQL 生成用云端、解读用本地"，但没写清为什么。
实际上这个划分是核心设计判断：

- 生成 SQL 的 LLM 输入是 Knowledge Retrieval 的表结构（Schema），
  只有表名、字段名、字段含义，不含任何业务数据 → 可以用云端
- 解读结果的 LLM 2 输入是 SQL Query 的真实结果，
  包含客户姓名、消费金额 → 必须本地处理

验证过实际数据流：
- LLM (DeepSeek-V3, 云端) context = Knowledge Retrieval.result
- LLM 2 (qwen3.5:4b, 本地) context = SQL Query.text

## 关键认知

"表结构"和"业务数据"是两回事：
- 表结构是数据库设计信息，可以给云端
- 业务数据是实际存储内容，不能出内网

这个边界划清楚，就能在保证隐私的前提下用更强的云端模型。

## 权衡

| 维度 | 结果 |
|---|---|
| 隐私 | 业务数据 100% 不出内网 |
| 精度 | SQL 生成用云端 V3，优于 4B 本地模型 |
| 成本 | 云端只处理 Schema，约 2700 token |
| 性能 | 本地解读是瓶颈，20s 占 80% 耗时 |

性能瓶颈是主动接受的代价，用延迟换隐私。
